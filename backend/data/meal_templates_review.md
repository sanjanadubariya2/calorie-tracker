## How the checks work

- **Serving weight:** the catalogue's grams for one household unit, compared with typical ranges (e.g. bowl 120–300 g, idli 30–60 g). A generic range only raises a question: each flag carries the assessment from the serving-weight audit (`data/serving_weight_audit.md`), and a catalogue value changes only with a traceable source or explicit approval. Audited-plausible weights are *info*; the rest are *review*.
- **Meal energy:** the base meal at default servings against typical ranges (breakfast 250–600, lunch 400–850, dinner 400–850, snack 100–350 kcal) is an *info* note only. Calorie ranges are soft recommendation targets, never a reason to change portions, so no portion change is proposed from them.
- **Name:** a template name that mentions an optional component is flagged for review, because the base meal doesn't include it. (Recommendations match exclusions and dislikes against the required components, so such a name never removes the base meal.)
- **Decisions** applied or rejected by the reviewer are recorded in `data/meal_templates_decisions.csv` and shown per template. Open flags and decisions together are in `data/meal_templates_corrections.csv`.

## How to review

1. For each template, decide in `data/meal_templates_review_status.csv`: `approved` (individually verified), `approved_provisional` (usable, not individually verified), `needs_correction` or `rejected`, with your name, a timestamp and (for all but `approved`) notes. `pending` means not reviewed.
2. Changes to the draft are made by editing `data/meal_templates_draft.csv` and recording them in the decisions file.
3. Rerun `python -m app.cli meal-templates-report`. Approval in the database is a separate step.
